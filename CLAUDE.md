# Project rules

A puzzle game on accurate classical electrodynamics. `SPEC.md` describes the game, `PHYSICS.md` the implemented physics and its validation, `README.md` how to run it.

## Physics accuracy
- Any change to physics or numerics updates `PHYSICS.md` in the same commit: the model, the method, and the measured test results. `PHYSICS.md` is the source; `python scripts/physics_pdf.py` typesets it into `PHYSICS.pdf` (pandoc with `docs/physics/filter.lua`, LuaLaTeX with `docs/physics/main.tex`; generated, not committed): run it after editing. New formulas may be written as LaTeX math between `$…$` (GitHub and the PDF render it); backtick spans are set as code (paths, identifiers) or as Unicode formulas.
- Validation tests compare against analytic or independent results. Set their thresholds from the target accuracy before measuring. If a threshold must change, document why in `PHYSICS.md`; never loosen one just to make a test pass.
- Symmetry and conservation tests are mandatory (the owner, 2026-10-20) for every algorithm that implements physics: (1) the system's symmetries: a symmetric setup gives a symmetric solution, and any breaking of it is explained; (2) the symmetries of the equations of motion (their Lagrangian or Hamiltonian) and the conservation laws they imply (Noether: energy, momentum, angular momentum, charge, canonical momenta); (3) the background's, passive ones: translations, rotations, boosts (Galilean or Lorentz, as the model is); (4) discrete ones: parity (B a pseudovector), time reversal (B flips), charge conjugation, their products, and the model's scalings (what stays the same when mass, charge, speed and field are scaled together). Each is tested against the exact transformed solution, with a threshold from the target accuracy, and PHYSICS.md (§ Symmetries) records how well and over what time each holds, so that no numerical method silently breaks one.
- Open problems (questions the literature does not answer and that could not be derived in reasonable time) go into `docs/OPEN_PROBLEMS.md`, with what was searched and tried and the workaround in use (the `open-problems` skill).
- The authoritative trajectory path is f64 on the CPU and deterministic: no fused multiply-add, a fixed summation order, and elementary functions (`sin`, `exp`, `ln`, `powf`, `atan2`, …) from the `libm` crate, never the standard library's (they call the platform's C library, which differs between Windows and Linux; `clippy.toml` disallows them). The GPU is for visuals only.
- Every shipped level must have a verified reference solution for every shot, and neglected radiation below 1e-10 of the launch energy (`crates/level/tests/levels.rs`).
- Golden hashes (`levels/golden_hashes.json`) change only when the physics or the levels change intentionally. `UPDATE_GOLDEN=1 cargo test --release -p level --test determinism` rewrites them all (about an hour); with `GOLDEN_ONLY=<part of a level's name>` it computes and updates only those (a new level's in a minute or two) and keeps the rest.

## Sandbox completeness
Every level that ships must be reproducible by hand in the sandbox.
- `crates/game/src/level_editor.rs` edits every field of the level format. Each level type is destructured exhaustively, with no `..`. A new field in the level format therefore fails to compile until it gets a control there, or is explicitly marked as not user-editable with a reason.
- The editor ranges are shared constants. `check_editable` validates each level against them, and the test `all_levels_are_reproducible_in_the_sandbox` runs it on every file in `levels/` and `levels/custom/`.
- A new element kind, coil shape or other level feature needs a sandbox tool or control in the same change.

## Workflow
- Before committing: `cargo fmt --all`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`. The heavy per-level tests (golden hashes, reference verification, neglected radiation) skip a level whose file and test program are byte-identical to a passing run (`level::run_cache::TestPasses`, `target/test-passes`): a new level costs minutes, a change to the physics or the level code reruns them all. The owner (2026-10-20): a full run (`EM_TEST_FULL=1`) every few levels, not every time; don't overdo the process.
- Level descriptions write formulas as LaTeX between `$...$` (in Python strings, double the backslashes); `scripts/levels.py` renders them with MathJax into `levels/math/` (Node.js; `npm install` in `scripts/math` once). Formulas are sized to the interface font's x-height (`math.rs`: 0.52 em): if the font changes, measure it again. A formula is never broken across lines: write long relations as several `$...$` split at relation signs (they wrap between pieces); `levels.py` warns about formulas over 30 ex (~60 % of the panel), and the game shrinks one wider than the panel to fit.
- Levels: `scripts/levels.py` is the single source of truth (curriculum order, designs, automatic detector placement); rebuild with `python scripts/levels.py`. Measure difficulty with `cargo run --release -p generator -- analyze levels/[0-9]*.json` and keep `docs/LEVELS.md` up to date. Level tools: `generator {solve,check,normalize,analyze}`. `analyze` logs progress and slow evaluations to stderr: read it before assuming a long run is just slow.
- Resource budgets: `crates/level/src/cost.rs` (sandbox meters; `generator check` prints them). A new solver with a linear system must report its build cost through `LevelField::setup_cost`.
- Curriculum rules: every new element or concept gets an easy introduction level first; within a chapter difficulty and the number of elements needed rise on average.
- Visual checks without touching the desktop: `EM_CAPTURE=out.png EM_LEVEL=<1-based> [EM_LEVEL_FILE=<level.json>] [EM_SANDBOX=1] [EM_SHOT=<1-based>] [EM_DISTURBANCE=<1-based>] [EM_MAP=potential|magnetic|waves|particle|total|electric|energy|current|heat|off] [EM_QUANTITY=E|S] [EM_PART=total|own|exchange|external] [EM_TRACERS=1] [EM_AVERAGE=0] [EM_RANGE=<decades>] [EM_GAIN=<decades>] [EM_ZOOM=<0.1-1>] [EM_FOCUS=<supply number>] [EM_GRID=<1-4>] [EM_PLACE=reference|<json>] [EM_TIME=<t>] [EM_RAD_ONLY=1] [EM_LINES=1] [EM_HARDCORE=1] [EM_TAU=<τ>] [EM_HOVER=<x,y>] [EM_PROBE=1] [EM_MAP_AT=<frame:map,...>] [EM_LEVEL_AT=<frame:level,...>] [EM_MINIMIZE=1] [EM_FRAME=<n>] [EM_WAIT=1] [EM_SPHERE_TEST=1] [EM_MODEL=1] [EM_SCALES=1] target/.../game` opens the level, saves a screenshot of its own window at frame `EM_FRAME` (default 120; the game runs at several hundred frames per second; with `EM_WAIT=1` at the first frame from then on where the verdicts are in) and exits. `EM_GAIN` sets a tube map's gain, `EM_ZOOM` a tube level's zoom on the board's centre, `EM_FOCUS` holds a supply in focus (its electrodes outlined, as when its slider is hovered). `EM_SPHERE_TEST` adds a metal sphere at frame 10 and removes it at frame 60 (regression check that stale computations are abandoned). `EM_MODEL=1` opens the "Physics model and its limits" section, `EM_SCALES=1` the "Scales" one. `EM_TAU` sets the maps' time average (a meter's time constant), `EM_HOVER` shows the inspection tooltip of the board point x,y (with `EM_PROBE=1` the probe's, as the I key holds it: every registered source's values there, `probe.rs`), `EM_MAP_AT` switches the map at the given frames (a regression check of the field maps' playback), `EM_LEVEL_AT` selects the given 1-based levels at the given frames (a check that no view of one level stays over the next), `EM_MINIMIZE=1` minimizes the capture's own window at frame 20 and restores it at frame 40 (a check that minimizing does not crash). Never send clicks or keys to the desktop.
- `generator trace <level> [--flight N] [--every N]` prints a reference flight (t, x, y, |p|).
- The generator caches tube runs, hash-locked (`level::run_cache`): each record is stored under the hash of the level (all of it), the placement, the resolution and the run's end, and the generator's own executable (a rebuild is another engine), in `target/run-cache` (or `EM_RUN_CACHE`). The runs are deterministic, so a record is bit for bit the run's. `--no-cache` (or `EM_NO_CACHE=1`) computes every run; `--verify-cache` reruns every hit and stops on any difference. `check --json` and `window --json` print their results as JSON.
- `generator scan <level> [placements.json] [--samples]` prints, for each placement (default: the reference), every flight's outcome, verification status and end state (t, x, p) as JSON at full precision (tube and beam levels: their goals' values and error bars): the game's numbers for the level documents.
- Level documents (`docs/levels/README.md`): each level's physics derived from first principles in `docs/levels/<slug>/doc.tex` (LaTeX, class `docs/levels/leveldoc.cls`), every number computed by its `calc.py` independently of the game and compared with the game's (`game.json`, from `generator scan`); `python scripts/level_docs.py {status,new,game,calc,check,build}`; the PDFs (`docs/levels/pdf/`, generated) open from the level panel. When a level or the physics changes, `check` reports the affected documents' game data stale: refresh with `game <slug>`, rebuild, and fix any comparison that fails (never by widening a tolerance). Authors follow `docs/levels/GROK.md`.
- `generator tube-scan <level> <placements.json> [--refine N]` (tube levels) prints, for each placement in the file (a list of placements, each a list of elements), the preview's current into every electrode over the goal's window, what left the board, the potential goals' measures, where each projectile ended, and the macroparticles in flight with their weights: the tool for designing tube levels (then `check` the chosen reference). `--refine 2` runs at the verification's resolution, higher values check convergence; `--particles F`, `--softening F` and `--emitter F` scale one resolution alone; `--trace E` also prints electrode E's (1-based) potential every step (`trace t V`: a tank's oscillation).
- `generator tube-field <level> [--every T] [--end T]` (tube levels) runs the electromagnetic field of the reference's preview (`level::tube_em`) and prints the power radiated out of the board against an output's load R⟨I²⟩ (the magnetron's antenna was sized with it), and the field's energy with its magnetic part, the field's own and the maps' (a closed box's smoothed).
- `generator window <level> [--steps N] [--element K] [--from V] [--to V]` prints, for each power supply and plate of the reference (or its Kth element alone: run the sliders in parallel), the intervals of its potential that solve the level, each evaluation logged to stderr. The default (240 steps over the whole slider) takes many hours on a metal's tube level, where a run takes 20 s to minutes and a supply far off (its current or Hall voltage reversed, the field at the slider's end) the longest: scan each slider alone over the half that can solve, with steps landing on the slider rule's points (0, the ends, the halves' middles) and the 5 % about them (e.g. `--element 3 --from -24 --to -2 --steps 11` on a ±40 slider). Potentials are sliders over a range symmetric about 0 (the owner): choose each level's range so that no solving interval contains 0, an end, or the middle of either half (`levels.py` `slider`; test `slider_ranges_hide_the_answer`).
- Levels showcase everything feasible (the owner, 2026-10-20: a priority; the game exists to show electromagnetism's physics and build intuition): every control the player has (sliders, element values and positions, cuts, …) spans all the behaviours the model can produce within reason (a solenoid from straight paths to small local circles of the carriers, a supply from nothing to strong effects), the views make those behaviours visible, and the level's answer is picked from among them. A slight rise in difficulty is the accepted price, but the level stays solvable with a comfortable solving interval (at least about 5 % of a slider's range, as `generator window` measures it) that still avoids 0, the ends and the halves' middles.
- Every level shows its scales (the owner, 2026-10-20: important): for each measurable quantity the typical real-world magnitude where its phenomena occur (an order of magnitude is enough, e.g. a few eV, mT, µm, ns; the grid's cell where it makes sense), and the relative scales that decide its physics (the dimensionless ratios such as ω_c τ or qEℓ/kT: what stays the same when the setup is scaled uniformly; e.g. a field too weak relative to the rest does not bend the paths), in a visible place in the game. Plots have axes with ticks and named quantities (game units, with the real-world order of magnitude where it helps).
- Pairwise element check: `python scripts/pairs.py [--gui] [--only <element>] [--separations 1 2]` puts every element next to every other (far to overlapping, Newtonian and relativistic) and runs each case through the game's worker (`--gui`: also the game itself in capture mode, which catches render-thread panics and panel overflows). Run it after adding an element kind or level feature, and add the feature to its `ELEMENTS`. Setups the physics cannot compute must be refused by `Level::setup_issues`, not crash or hang.
- egui: keep every Grid row narrower than the side panel; an overflowing row makes egui draw a stray full-height line.
- Every element of the interface is explained, without clutter (the owner): a mark drawn on the board that is not a hoverable object (arrows, chevrons, glows, beads, colour codes) gets a row in the board's legend (`crates/game/src/legend.rs`: a swatch in its colours, a few words, the explanation on hover); panel text is a short line with the detail on hover (`ui::explain`), never a paragraph of small print; controls carry hover text.
- Long computations (`docs/PROGRESS.md`; `/progress` shows where they are, read-only): estimate per item and in total before launching (within 50 % is fine) and say it; run them through `scripts/progress.py run` with a pattern counting this computation's items; split anything of an hour or more into chunks of at most an hour that save their results and run one after another by themselves (`progress.py chain`): an interruption must not lose more than an hour of work.
- Audits are archived in `audits/` (`audits/README.md`: the audited commit and the commit that fixed it, with a verdict per remark in each folder's `RESOLUTION.md`); the next audit reviews `git diff <last fix>..HEAD`.
- Commit messages end with the co-author line used in the history.
